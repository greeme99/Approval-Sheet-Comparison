# 7단계 개발 수명주기

## 사용 시점

신규 제품, 여러 화면이 있는 웹앱, 데이터 처리 도구처럼 요구사항과 구현의 연결이 필요한 작업에서 사용한다. 기존 작은 수정은 필요한 단계만 적용한다.

## 0. 개발 계획 구체화

산출물을 만들기 전에 다음을 결정한다.

- 해결할 사용자 문제와 현재 대안
- 주요 사용자와 의사결정자
- 측정 가능한 성공 기준
- 포함·제외 범위
- 데이터 출처·민감도·보존 정책
- 우선 운영 환경과 배포 형태
- 외부 서비스·AI·네트워크 사용 정책
- 일정 또는 단계별 승인 방식

결정할 수 없는 항목은 `가정`으로 기록하고, 결과를 크게 바꾸는 경우만 사용자에게 질문한다. 계획에는 각 단계의 산출물, 승인 게이트, 구현·시험 완료 기준을 포함한다.

## 1. 요구사항 정의

SRS는 구현 방법보다 필요한 결과를 정의한다.

- 배경, 문제, 목표, 사용자
- 포함·제외 범위
- 기능 요구사항 `FR-*`
- 비기능 요구사항 `NFR-*`
- 보안·개인정보 요구사항 `SEC-*`
- 데이터 요구사항 `DATA-*`
- 가정, 제약, 용어
- 요구사항별 검증 가능한 수용 기준

좋은 수용 기준은 관찰 가능해야 한다. “빠르다” 대신 “대표 입력을 기준 장비에서 30초 이내 처리한다”처럼 쓴다.

## 2. 기능 정의

PRD/FS는 각 요구사항이 어떻게 동작하는지 결정한다.

- 정상 흐름과 대안 흐름
- 입력, 출력, 상태 전이
- 검증, 우선순위, 중복·충돌 처리
- 빈 상태, 로딩, 실패, 재시도
- API·파일·스키마·이벤트 경계
- 권한과 데이터 수명주기
- 요구사항 ID와 기능 ID 연결

오류 메시지는 원인과 사용자가 취할 수 있는 조치를 함께 제시한다.

## 3. 정보 구조

IA는 기능 목록이 아니라 사용자가 목표에 도달하는 경로다.

- 사이트맵 또는 화면 트리
- 시작점과 핵심 작업 경로
- 화면 간 전환 조건
- 전역·지역 탐색
- 필터·정렬·선택 상태의 적용 범위와 보존
- 사용자 역할별 접근
- 종료, 취소, 재시작 경로

필터는 결과 건수뿐 아니라 관련 지표·표·시각화 등 약속된 모든 렌더러에 같은 범위로 적용되어야 한다.

## 4. 화면 설계

와이어프레임은 레이아웃과 상호작용을 검증한다.

- 실제 콘텐츠를 사용한 핵심 화면
- 입력 전, 처리 중, 결과 없음, 오류, 성공 상태
- 주요 행동과 되돌리기·취소
- 데스크톱·모바일 또는 목표 해상도
- 키보드 순서, 포커스, 레이블

가능하면 브라우저에서 열리는 클릭형 HTML을 만들고 실제 상호작용을 시험한다.

## 5. UI 디자인

UI 시안은 구현 가능한 토큰과 상태 규칙을 제공한다.

- 색상, 타이포그래피, 간격, 테두리, 상태 토큰
- 컴포넌트별 기본·호버·포커스·비활성·오류 상태
- 색상 외 텍스트·아이콘을 포함한 상태 구분
- 대비, 확대, 키보드, reduced motion
- 제품과 사용자 업무에서 나온 한 가지 식별 가능한 디자인 특징

장식보다 정보 위계와 업무 속도를 우선한다.

## 6. 개발

- 저장소 지침과 기존 구조를 먼저 따른다.
- 승인된 범위에 필요한 최소 구조를 선택한다.
- 핵심 로직과 UI·I/O를 분리해 독립 시험 가능하게 한다.
- 입력 검증, 데이터 손실 방지, 보안 경계는 단순화를 이유로 생략하지 않는다.
- 버그는 가능하면 재현 시험을 먼저 만든다.
- 구현 기록에는 요구사항 ID, 변경 파일, 결정, 시험, 미검증을 남긴다.

## 7. 테스트

위험과 변경 범위에 맞춰 다음 중 필요한 것을 수행한다.

1. 단위 시험
2. 통합 시험
3. 정적 검사·타입 검사
4. 빌드
5. 사용자 흐름 또는 E2E
6. 목표 운영 환경 실기기 검증
7. 성능·보안·접근성 검사

테스트 보고서는 실행 명령, 환경, 기대·실제 결과, 결함, 수정·재시험, 미검증, 최종 판정을 기록한다.

## 단계 변경 관리

요구사항이 바뀌면 해당 ID의 SRS, 기능 명세, IA/화면, 구현, 테스트를 함께 갱신한다. 문서 순서가 완료를 의미하지 않으며, 추적성과 검증 결과가 완료를 결정한다.
