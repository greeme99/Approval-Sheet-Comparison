# 요구사항 추적 규칙

## ID 체계

| 접두어 | 용도 | 예시 |
|---|---|---|
| `FR` | 사용자 기능 | `FR-001` |
| `NFR` | 성능·사용성·운영 품질 | `NFR-001` |
| `SEC` | 보안·개인정보·권한 | `SEC-001` |
| `DATA` | 데이터 출처·품질·보존 | `DATA-001` |
| `F` | 기능 명세 항목 | `F-01` |
| `TC` | 테스트 케이스 | `TC-FR-001-01` |

기존 조직의 ID 체계가 있으면 그것을 우선한다. ID는 내용이 변경되어도 재사용하지 말고, 폐기된 요구사항은 상태를 `폐기`로 남긴다.

## 최소 연결

```text
사용자 목표
  -> 요구사항 ID와 수용 기준
  -> 기능 규칙 또는 인터페이스
  -> 화면/정보 구조(해당 시)
  -> 구현 위치
  -> 테스트 케이스와 실제 결과
```

## 추적 표 권장 열

`요구사항 ID | 요약 | 기능 ID | 화면/인터페이스 | 구현 위치 | 테스트 ID | 상태 | 근거`

구현 위치는 파일 목록을 무분별하게 나열하지 말고 핵심 모듈 또는 진입점을 기록한다. 시험 상태는 `미실행`, `통과`, `실패`, `차단` 중 하나를 사용한다.

## 변경 시 점검

- 수용 기준이 관찰 가능한가?
- 기능 명세가 요구사항의 예외와 실패를 정의하는가?
- UI 상태가 기능 상태와 일치하는가?
- 테스트가 문구 존재가 아니라 실제 동작을 확인하는가?
- 운영 환경에서만 확인 가능한 항목이 미검증으로 남아 있는가?
